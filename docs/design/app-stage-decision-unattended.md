# 决策备忘录：无人值守自动化（隐藏 runner 重议）

**状态：决策记录（M6f）。** Phase 3 遗留项的裁决，防"计划里提过一嘴"被未来读者当成已决或已否。规范引用：app-stage.md v0.0.6 L172（invoke 路由只进可见容器）、L154（无隐藏 runner）。

## 背景

v0.0.5 砍掉隐藏 runner 与资源池体系时，把「无人值守自动化（隐藏 runner 届时重议）」挂到 Phase 3。M6 到位后重议条件成熟：水位/历史/回退（M6a/b）、导入第二入口（M6c）、权限模型提案（M6d，未定案）、迁移与资产回收（M6e）。

## 裁决：**不进入实现，维持"无隐藏 runner"，重议窗口移至权限模型定案后**

理由（按权重序）：

1. **前提能力未定案。** 无人值守的每一项真实场景（定时拉数据、监听触发、夜间批处理）都需要应用侧至少 `agent.trigger` 级别的受控能力（M6d 提案 v0.0.1 红队裁决「需修订后再评」——致命项正是能力语义空心）。在能力权限模型定案前建 runner，等于给未定案的权限面预先造一个常驻行使者。
2. **可见性原则没有便宜的降级。** "AI 操作全程可见"（用户拍板）在无人值守下的对应物是完整的调度可见性（谁在何时为何触发、跑了什么、写了什么）——这不是横幅/时间线的现有形态能承载的，是一个与 Presence 同量级的设计题。v0.0.5 的教训（资源池体系过度设计）在这里同样适用：没有第一手场景压测就建体系，建出来的只会是猜的。
3. **重放面缺位。** 无人值守把"用户不在场"变成常态，则每个自动动作必须有可回放的审计记录。M6a 的 history.jsonl 是安装史不是动作史；动作留痕（能力调用日志）在 M6d 评审 H7 中刚被指出缺位。留痕面先于 runner。

## 触发重开的条件（满足其一即可重新上桌）

- 权限模型 v0.0.2+ 定案且 `agent.trigger`（或后继词）进入可实现状态；
- 出现一个用户亲述的、周频以上的真实无人值守场景（不是假想场景）；
- 官方 Host 出现可复用的定时/事件调度原语（则成本结构改变，重估）。

## 对现状的约束（防漂移）

- 现行「无可见容器 → 可行动错误」行为**不是缺陷**，是这条裁决的运行时表达；不得在错误文案里承诺未来能力。
- 本备忘录不产生任何代码、工具或 schema 变更。
